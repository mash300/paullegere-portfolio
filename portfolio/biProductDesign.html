Early Concepts & Wireframes

A scheduling feature became a systems-design challenge: how should brewers plan work when batches, equipment, and production stages depend on one another?

Brewers Insight is software for planning and tracking brewery production. I independently owned the early UX research and planning for a new Brew Planner MVP: researching comparable products, mapping operational workflows, and defining how scheduling, batch configuration, transfers, and exceptions should behave.

I was the sole product and UX designer on the project. My deliverables included research, system and user-flow diagrams, early sketches, interaction rules, and conceptual mockups. Devin developed the interface using my concepts and documentation. I did not design the final visual interface or write the production application code.

The work expanded beyond a timeline view because a change in one part of the production schedule could affect equipment availability and downstream processes.


Early Brew Planner concept showing the production timeline and batch-configuration sidebar. Included to illustrate the UX planning, not to claim final UI design.

MVP Concept: Brew Planner


Problem

The platform lacked a centralized way to visualize production schedules across tanks, batches, and timelines. Planning was fragmented, increasing the risk of scheduling conflicts and operational downtime.

The core challenge was defining predictable behavior across interconnected workflows, not simply arranging a scheduling screen.

The planner needed to:

  • Integrate with existing production data
  • Represent time-based dependencies
  • Surface conflicts and overlaps
  • Scale with future operational complexity
The Process

System Mapping

Mapped how recipes, brewhouse turns, conditioning, equipment assignments, transfers, and packaging fit together across time. These dependencies shaped what the planner needed to show and when.

Interface Structure

Defined timeline interactions, sidebar configuration flows, and the decision points users would encounter when editing a plan. For example, changing a brew-turn date could trigger conflicts that needed to be surfaced before changes were applied.

Implementation Awareness

I documented the intended interactions and requirements with existing production data and technical feasibility in mind. Devin subsequently built the interface based on my UX concepts. The final visual UI and application code were outside my scope.

Outcome

  • Defined an MVP framework for a production-planning feature that did not previously exist
  • Documented interconnected workflows and exceptional states for development
  • Connected the planning concept to existing recipes, production stages, and equipment data
  • Devin subsequently implemented the Brew Planner interface based on my UX concepts and documentation
Strategic Takeaways

  • A small scheduling change can have consequences across an entire production plan
  • Edge cases and confirmation states should be part of the primary workflow, rather than added later
  • Clear interaction rules make complex requirements easier to discuss with engineers
  • Operational software needs a readable overview without hiding important dependencies

Planner User Flows

Rather than treating the planner as a set of isolated screens, I mapped the actions and dependencies between creating batches, adjusting brew dates, allocating conditioning volumes, and reviewing historical production. I also explored the related Forecasting Report as a separate workflow connected to the same production context.


System Workflow Overview

Overview of the documented interactions across planning, batch configuration, transfers, reporting, and forecasting. The detailed examples below explain why particular decisions mattered.





Key Workflow Examples

These examples show the decisions behind the flows: the operational need, the constraint or edge case, and the behavior I proposed in the MVP documentation. They are UX planning artifacts, not claims of authorship over the final production UI.



Creating a Production Batch

Design challenge: Make it possible to plan a new batch without making the brewer re-enter information already held in the system. The flow begins from the timeline, uses the selected recipe as a starting point, and exposes the production stages that need configuration.

UX decision: Keep the batch setup in a contextual sidebar so brewers can configure brewing, conditioning, and packaging while retaining sight of the schedule. The interaction must connect a local edit to the broader production plan.


Handling Scheduling Conflicts

Edge case: In the documented Mosaic IPA scenario, two brewhouse turns initially occur on the same start date. Moving the second turn to the following day extends the production timeline and can conflict with other planned work.

UX decision: The flow presents the consequences before applying a change. A confirmation gives the brewer a choice: allow the system to adjust affected plans or keep control and select dates manually. This illustrates why a scheduling edit cannot be treated as an isolated form update.


Splitting Fermentation into Packaging Runs

Design challenge: A batch might need to be divided among conditioning tanks or later outputs, while still accounting for its original volume. The flow makes the total volume and unit of measurement visible as the brewer creates additional transfers.

UX decision: Each transfer has a destination, timing, and quantity. Adding transfers creates separate scheduled processes; deleting a transfer requires confirmation, with its allocated volume returned to the starting total. That guards against losing track of material when plans change.


Reviewing Historical Brews

Edge case: Past brew runs need to remain visible as operational reference without appearing editable like upcoming work. In the flow, historical processes are greyed out and treated as read-only.

UX decision: Selecting a historical process offers contextual details and a path to a Brew Run History report, rather than controls for changing a completed run. The distinction helps preserve the meaning of historical records within the same planner view.


Visual Identification Through Colour

Design goal: Help operators recognize a brew at a glance in a busy production schedule. I explored assigning a consistent colour to each brew run, reflecting colours already associated with a brewery's products, such as red for an Irish Red, blue for Mosaic IPA, or brown for a chocolate stout.

Interaction detail: The colour picker let an operator preview a selection, use saved swatches or a custom hex value, and then apply or cancel the change. When applied, the chosen colour carried through the brew's planner processes and associated sidebar sections. This kept the same visual reference as the user moved between the timeline and batch details.

UX consideration: Colour was intended to support recognition, not replace labels. Brew names and process information remained visible. I treated this as a secondary usability improvement rather than a requirement for the core scheduling workflow.

Forecasting Material Demand

Connected but separate: The Forecasting Report is not another Brew Planner screen. It is a related reporting workflow that uses planned production and recipe information to explore expected material requirements.

UX decision: I mapped filtering by date range, recipe, material grouping, category, and supplier, along with options to focus on shortages and export results. The challenge was making a large set of reporting choices understandable without obscuring the purchasing decisions they support.


Reflection


Brew Planner did not exist when I joined. I worked independently as the project's sole product and UX designer, researching the operational problem, defining the MVP direction, and documenting the workflows, dependencies, and edge cases. The project also involved the founder, a production manager, and Devin, the developer who built the interface based on my concepts.

The most revealing problems were not the obvious ones. Moving one brewhouse turn could disrupt other plans. Splitting a conditioning volume introduced accounting and deletion rules. Historical records needed to stay accessible without being confused with editable work. These decisions shaped how the system should behave, not just how it should look.

I came away with a stronger appreciation for designing around real operational processes, communicating interaction rules clearly, and considering engineering constraints early. For complex products, a useful interface depends on understanding what happens before, during, and after each user action.
